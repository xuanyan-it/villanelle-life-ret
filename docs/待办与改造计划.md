# 项目待办与改造计划

## 1. 质量门禁

- [ ] 建立 PR 强门禁工作流
  - 范围: `typecheck + lint + unit + mock e2e`
  - 要求: 任一失败禁止合并；产出可追踪的 CI 报告链接。

- [ ] 建立发布前强校验工作流
  - 范围: `build + server test:e2e:real + frontend/electron e2e smoke`
  - 要求: 仅允许通过该门禁的 commit 进入 release 分支。

- [ ] 发布元数据与兼容性自动门禁
  - 范围: 发布流水线校验 `appVersion/contractVersion/modelVersion/gitSha`，并执行契约兼容窗口自动检查。
  - 要求: 缺失字段、格式非法或未声明破坏性变更时自动阻断发布。
  - 补充: 固化 `Validate -> Verify -> Integration -> Package -> Smoke -> Release` 阶段并输出审计记录。

- [ ] 建立失败分级与告警通道
  - 范围: PR 门禁失败、nightly 失败、发布门禁失败
  - 要求: 失败自动通知（邮件/IM）并附最小复现信息。

- [ ] 建立运营值班与告警升级流程
  - 要求: 明确值班角色、升级链路、响应 SLA 与复盘模板。

## 2. 测试体系

- [ ] 覆盖率阈值门禁
  - 范围: `server`、`frontend`、`electron`
  - 建议基线: statements/lines/functions >= 80%，branches >= 70%（后续再提高）。

- [ ] 测试门禁量化与不稳定用例治理
  - 范围: 必过任务矩阵、覆盖率阈值、flaky quarantine（owner + 过期时间）。
  - 要求: 文档阈值与 CI 门禁一致，`pnpm test:server` 收敛到全绿并纳入稳定门禁。

- [ ] Nightly real-e2e 自动化
  - 范围: 每日定时执行真实依赖链路（DB/worker/关键 API/UI）
  - 要求: 自动归档测试报告、失败快照与日志。

- [ ] 变异测试
  - 范围: `server/src/modules/*/service`、`shared/src/application/*`
  - 工具: `StrykerJS`
  - 门禁: 初始 `mutation score >= 60%`，稳定后提升到 `75%+`。

- [ ] 故障注入回归
  - 场景: DB 超时/不可用、worker 未就绪、模板缺失、鉴权失败、下载失败
  - 断言: 必须同时校验“状态码 + 用户提示 + 审计日志”。

- [ ] 容量评估与性能基线
  - 要求: 先定义压测口径、负载模型、容量阈值，再固化回归基线。

- [ ] 并发与压力回归
  - 工具: `k6` 或 `Artillery`
  - 场景: 恒定负载、突刺、长稳压（login/create/list/download）
  - 指标: `p95`、错误率、超时率、资源占用。

## 3. 安全与合规

- [ ] 云侧数据库暴露面与安全组基线落地（对照 ADR-014：compose 主库不映射公网；E2E 独立实例若开放专用端口须实例/口令隔离、强熵密码、优先安全组限源；轮换与巡检）
  - 范围: 测试/自托管 Runner 所在主机、任何含 Postgres 的 compose 覆盖文件与额外 E2E 数据库栈
  - 要求: 变更评审核对「哪一实例可公网、哪一实例仅内网」；事件后密码与密钥轮换闭环可审计

- [ ] 登录防爆破策略
  - 范围: 登录限流、失败次数阈值、冷却窗口、审计记录
  - 要求: 可配置并可单测 + e2e 验证。

- [ ] 生产 HTTPS 正式化
  - 要求: 仅使用受信任 CA 证书，禁止自签证书进入生产。
  - 部署: 在反向代理层统一 TLS 终止并固化加密基线。

- [ ] HTTPS 全环境回归计划
  - 范围: 开发/测试/生产证书策略、CI 证书注入、E2E 验证回填。

- [ ] 密钥治理自动化
  - 要求: 密钥仅通过 CI/CD Secret 或密钥管理服务注入，禁止手工散落。
  - 补充: 建立轮换周期、失效策略和应急替换流程。

- [ ] 审计日志合规增强
  - 要求: 补齐关键字段标准（who/when/where/what/result/requestId/eventId）
  - 补充: 明确脱敏策略与保留周期，支持检索与追责。

- [ ] 威胁建模与年度复审机制
  - 要求: 形成统一威胁建模模板，纳入年度复审节奏与结论追踪。

- [ ] 数据保留与合规删除流程
  - 要求: 明确保留时长、删除触发条件、审批与审计留痕。

## 4. 跨环境与发布稳定性

- [ ] CI 跨平台矩阵
  - 范围: `windows-latest + ubuntu-latest`
  - 目标: 避免“开发可用、部署异常”的平台漂移。

- [ ] 运行时版本基线固化
  - 范围: Node/pnpm/Python/Postgres/Electron
  - 要求: 在文档与 CI 中强约束统一版本。

- [ ] 真实依赖容器化基线
  - 范围: Postgres + server real-e2e 依赖
  - 目标: 降低本地/CI/生产环境差异。

- [ ] Python 评估链路并发治理
  - 要求: 评估 worker pool（多进程）或推理服务化方案，并定义排队上限、超时与退避策略。

## 5. 可运维性与可观测性

- [ ] 关键 SLI/SLO 建立
  - 指标: 可用性、响应延迟、错误率、关键任务成功率
  - 要求: 对应仪表盘与阈值告警可落地。

- [ ] 日志与追踪关联增强
  - 要求: 前后端统一 `requestId/eventId` 贯穿，错误可端到端追溯。
  - 补充: 产线日志采集、分级、留存策略标准化。

## 6. 资产与模型治理

- [ ] 大体积资产统一迁移到单独资产仓库并建立同步机制
  - 范围: `assets/models/artifacts`、大体积字体等非代码资产。
  - 要求: 主仓库仅保留 manifest 与校验信息（版本、SHA256、大小、来源地址）；通过统一脚本在开发机、CI、发布流程执行拉取与完整性校验。
  - 交付: 增加 `assets:sync` 命令、同步脚本、资产仓目录规范、失败重试与校验失败阻断策略。

- [ ] `assets/models` 与 `assets/templates` 版本治理
  - 要求: 命名规范、回滚策略、变更审计与发布对账。

- [ ] 模型装载清单 `MODEL_MANIFEST` 治理落地
  - 要求: 定义清单结构、加载顺序、校验规则与回滚策略，并接入发布门禁。

- [ ] Electron 共享资产装箱策略
  - 要求: 明确是否内置模型、是否外挂目录、升级覆盖规则与回滚策略。

- [ ] `MODEL_DIR` 与 `TEMPLATE_DIR` 部署约定文档化
  - 范围: dev/staging/prod
  - 要求: 给出目录结构、覆盖顺序、回滚与排障手册。

- [ ] 评估结果响应追踪字段补齐
  - 要求: 评估相关 API 响应明确 `modelVersion` 与 `requestId` 的暴露策略，可通过响应体或统一 meta 暴露，并补单测/e2e。

## 7. 架构治理与文档流程

- [ ] 导入边界自动校验补齐
  - 范围: `frontend/server/electron/shared`
  - 要求: 用 lint 或同等机制自动阻断越层依赖。

- [ ] 例外治理流程自动化
  - 范围: 越层依赖等边界例外的审批记录、失效时间、到期提醒与回补校验。
  - 要求: 例外流程可审计、可追踪，不依赖人工记忆。

- [ ] 写接口幂等键机制落地
  - 范围: create 类写接口引入 `idempotencyKey`，覆盖协议、存储与冲突返回语义。
  - 要求: 补齐单测、集成测试与跨传输一致性验证。

- [ ] 测试策略文档化
  - 内容: 测试分层、门禁矩阵、何时跑 mock/real e2e、发布验证清单。
  - 输出: 根目录 `docs/testing-strategy.md` 或同等文档。

- [ ] 运维 Runbook 文档化
  - 内容: 常见故障处置、回滚流程、密钥轮换、证书续期。
  - 目标: 降低人员变动带来的运维风险。
