# PRD-005 中断评估（单个&批量）

## 1. 目标

实现“中断评估（Interrupt Evaluation）”能力，使用户在单条或批量导入评估过程中可以：

- 中止当前正在执行的评估任务（协作式取消）
- 在页面刷新后仍能恢复查看正在执行的任务进度（不依赖 `sessionStorage`）
- 在取消后保留已完成的记录结果，不回滚已写入的结果
- 重新导入时追加新记录（不自动去重覆盖），并遵循“同一用户/同一机构仅允许 1 个 active job”的约束

## 2. 背景

- 评估过程需要异步化，以支持长耗时任务的进度展示与可中止能力。
- 批量导入若仍采用“前端逐条请求+同步执行”，会造成大量 HTTP 请求与交互阻塞。
- 页面刷新会导致前端队列状态丢失，需要后端提供“active job 列表”用于刷新恢复。
- 取消需要明确语义：已完成的要保留，未完成的要停止并标记为取消。

## 3. 范围

### In Scope

- 运行形态范围：Web 与 Electron 均启用本 PR 能力，保持端间业务语义一致（单条异步评估、批量入队、轮询进度、取消中止、刷新恢复）。
- 引入/使用后端 `evaluation_job` 与 `evaluation_job_item` 作为评估任务模型（单个与批量复用同一套概念）。
- 支持以下 RESTful 接口（见第 4.2 节接口契约）：
  - 批量入队：`POST /api/record/evaluation-jobs`
  - 任务状态：`GET /api/record/evaluation-jobs/:jobUuid`
  - active 恢复列表：`GET /api/record/evaluation-jobs/active`
  - 取消（PATCH）：`PATCH /api/record/evaluation-jobs/:jobUuid`
- 前端使用轮询刷新进度（轮询间隔 2 秒），并在任务推进时刷新记录列表展示。
- 前端“中止”按钮仅触发取消（不会清空前端队列），并在取消后显示“正在中止中”反馈。
- 协作式取消语义：
  - `cancelRequested=true` 后，runner 在检查点停止后续评估
  - 所有 `pending/evaluating` 的 item 立刻标记为 `cancelled`（包含“当前正在执行的那条”）
  - 已完成（`succeeded/failed`）的 record 结果保留，不回滚
  - 已写回结果的 item 不会因为取消而回退
- 刷新恢复语义：不使用 `sessionStorage`，通过 `GET .../active` 恢复轮询。
- 重新导入语义：
  - 每次新导入都会创建新的 `evaluation_job`（新的 `jobUuid`）
  - 不自动覆盖/去重：旧记录保留，新记录追加
- active 限制语义：对同一 `instituteName`，同一用户最多存在 1 个 `pending/evaluating` 的 active job。

### Out of Scope

- 不修改 Python evaluation worker 的评估逻辑（worker 仍由后端控制调用时机）。
- 不提供服务器端“暂停后续继续”的精细恢复（本 PR 只保证取消后的协作中止与刷新恢复）。
- 不引入服务端对同批输入的自动去重/合并（追加语义保持）。

## 4. 设计说明

### 4.1 术语约定

- `evaluation_job`：一次评估任务的顶层容器，拥有 `jobUuid`，记录任务级状态（`pending/evaluating/succeeded/failed/cancelled` 等）。
- `evaluation_job_item`：任务内的单条评估项，对应输入中的第 `itemSeqNo` 条记录。
- `record`：最终展示与被打印/导出的记录实体。当前语义为“仅在评估成功后创建 record”，取消/失败不创建 record。

### 4.2 接口契约

1. 批量入队（创建 N 条 item，1 个 job）

- `POST /api/record/evaluation-jobs`
- Request body：
  - `instituteName: string`
  - `records: BaseRecordCreateRequest[]`（长度 >= 1）
  - `evaluationJobStart?: boolean`（是否立即启动 runner，MVP 直接支持）
- Response：
  - `jobUuid: string`
- 并发限制：
  - 若用户在该 `instituteName` 下已有 `pending/evaluating` 的 active job，则返回 `409 Conflict`
  - 客户端必须显式先取消旧 job（PATCH），并等待旧 job 不再处于 active（至少不再 pending/evaluating / status 变为 cancelled）再重试入队

2. active job 列表（刷新恢复）

- `GET /api/record/evaluation-jobs/active?instituteName=...`
- Response：
  - `jobs: BaseEvaluationJobStatusResponse[]`（最多 1 个 active job）
- 用途：
  - 页面刷新后恢复轮询
  - “中止”按钮获取当前正在执行的 jobUuid

3. 单个 job 状态（用于轮询）

- `GET /api/record/evaluation-jobs/:jobUuid?instituteName=...`
- Response：
  - job 状态字段 + 按 `itemSeqNo` 排序的 items 状态列表
- 前端轮询间隔：
  - 2 秒

4. 取消（RESTful PATCH）

- `PATCH /api/record/evaluation-jobs/:jobUuid`
- Request body：
  - `{ cancelRequested: boolean }`
- 语义：
  - 后端设置 job 的 `cancelRequested=1`
  - 将该 job 下所有 `itemStatus in ('pending','evaluating')` 的 item 立刻置为 `cancelled`
  - runner 在完成评估工作后写回结果前再次检查 `cancelRequested`，避免把取消中的 item 写成 `succeeded`

### 4.3 后端执行与数据写入策略

- 批量模式：
  - enqueue 时创建 `evaluation_job` + N 个 `evaluation_job_item`，不提前创建 `record`
  - runner 按 `itemSeqNo` 串行执行：
    - item 之间固定间隔 1 秒（首条不等待）
    - 调用 python worker 得到评估结果
    - 仅当评估成功时创建对应 `record`，并把 item 标为 `succeeded`
    - 评估失败则 item 标为 `failed`，不创建 `record`
  - 协作式取消检查点：
    - 每个 item 在开始评估前检查 `cancelRequested`
    - 评估完成后创建 record 前再次检查 `cancelRequested`，避免取消期间写入数据

- 单条模式（evaluationAsync）：
  - 创建 `evaluation_job` + 1 个 `evaluation_job_item`，并在异步 runner 里执行评估
  - 仅当评估成功时创建 record
  - 取消/失败时不创建 record

### 4.4 前端交互

1. 进度展示与轮询

- 使用轮询查询 `GET /api/record/evaluation-jobs/:jobUuid`，轮询间隔 2 秒。
- 记录列表刷新策略：
  - 当轮询结果中 `pendingCount` 发生变化时，触发列表刷新，使用户能看到已完成 item 的结果逐步落地。

2. 中止按钮（取消中止）

- 使用 cancel-only 行为：
  - 点击“中止”后仅发送取消请求，不清空前端队列状态。
- 用户反馈：
  - 点击“中止”后立即显示“正在中止中”
  - 当轮询发现任务不再 active（队列忙碌状态结束）时自动恢复按钮文案

3. 刷新恢复

- NewRecord 页面 mount 时调用 `GET /api/record/evaluation-jobs/active` 恢复 active job 状态。
- 恢复后继续轮询并刷新进度与记录列表。
- 明确约束：不使用 `sessionStorage` 作为任务追踪存储。

### 4.5 兼容性与风险

- 风险点：单条 `record/create(evaluationAsync)` 在任务完成前不会有真实 `record` 可查，前端需以 job/items 状态为准，不应假定立即存在 record。
- 资源消耗：轮询会带来额外请求，需要控制轮询频率与前端触发策略（本 PR 以 2 秒为基线）。
- 并发策略：同一用户/同一机构只允许 1 个 active job，避免评估 runner 并发竞争或语义冲突。

### 4.6 端间一致性（Web / Electron）

- 统一能力：两端均支持“单条异步评估、批量入队、轮询进度、取消中止、刷新恢复”。
- 统一语义：`evaluation_job` / `evaluation_job_item` 状态机、取消语义、active 唯一性约束保持一致。
- 统一列表语义：`record/list` 只展示已成功评估并落库的记录；取消/失败项不进入列表。
- 统一交互：底部进度条、"中止" 按钮、"正在中止中" 反馈与完成后收敛行为保持一致。

### 5.1 单元/类型检查

- [ ] Server typecheck 通过

### 5.2 功能测试（核心场景）

- [ ] 单条 `evaluationAsync`：可轮询看到进度/完成，并可取消且当前 item 不会写回成功结果
- [ ] 批量 enqueue 成功：
  - 返回 `jobUuid`
  - 轮询能看到 items 状态从 `pending -> evaluating -> succeeded/failed`
  - 仅成功项会出现在记录列表
- [ ] 批量取消语义：
  - `cancelRequested=true` 后当前正在执行的 item 以及其后的未执行项最终标记为 `cancelled`
  - 已完成成功项对应 record 保留；取消/失败项不创建 record
- [ ] 重新导入追加语义：
  - 取消后重新导入能创建新的 job（新的 jobUuid）
  - 新记录追加存在，不覆盖旧记录
- [ ] active 唯一性与 409：
  - 同一用户/同一机构 active 未取消前再次 enqueue 返回 `409 Conflict`
- [ ] 端间一致性：
  - Web 与 Electron 在单条、批量、取消、刷新恢复场景的行为与结果一致

### 5.3 边界场景

- [ ] 取消在评估非常快时发生：仍应保证至少不出现把已取消 item 误写成 `succeeded`
- [ ] 页面刷新发生在任务执行中：刷新后能恢复并继续轮询

## 6. 验收标准

- 用户在单条/批量评估进行中点击“中止”后：
  - UI 显示“正在中止中”
  - 当前正在执行项不会落库为 record（不会把当前 item 变成 `succeeded`）
  - 后续未执行项不会落库（标记为 `cancelled`）
  - 已成功完成项保留
- 页面刷新后：
  - 能通过 `GET /api/record/evaluation-jobs/active` 恢复 active job，并继续轮询展示进度与结果
- 重新导入后：
  - 旧结果保留，新的结果追加
  - 若未取消旧 active job，则 enqueue 返回 409 并由前端引导先取消后重试
