# Ret 架构事实与约束

更新时间：2026-03-30

## 1. 架构目标与非目标

架构目标：
1. 在 Web 与 Desktop 两种运行形态下提供一致的业务语义。
2. 通过 shared 契约层控制跨端接口、错误模型与数据结构的一致性。
3. 在医疗场景下满足可审计、可追踪、可回滚的工程治理要求。

非目标：
1. 不在本总纲中描述页面级实现细节。
2. 不在本总纲中承载迭代任务清单。
3. 不将未落地能力写成既有事实。

## 2. 架构边界

1. frontend 负责交互与视图状态。
2. server 负责 Web API、鉴权、业务编排与服务端持久化。
3. electron 负责桌面容器、IPC 与本地运行资源管理。
4. shared 是跨端单一事实源，包含 contracts、domain、application、config。
5. assets 是运行资产边界，包含 models 与 templates。
6. scripts 是仓库级工程脚本边界，统一承载根目录自动化脚本。

运行边界：
1. Web 形态：frontend -> HTTP(S) -> server。
2. Desktop 形态：frontend -> IPC -> electron。

## 3. 全局强约束

安全约束：
1. 生产环境必须 HTTPS。
2. 生产环境必须强 JWT_SECRET。
3. 鉴权严格模式固定启用，不提供生产绕过开关。
4. PostgreSQL：compose 主栈 `db`（业务/主测试库）不得对公网映射端口；若单独部署**仅用于自动化 E2E** 的实例并暴露专用端口（如宿主机 `15432`），须与主栈库**实例隔离**、**强且专用口令**、仅测试数据，并满足 `docs/adr/ADR-014-数据库暴露面与测试环境安全基线.md` 中的例外条款；禁止默认/弱口令与口令复用。

契约约束：
1. 跨端契约仅由 shared 定义。
2. 响应 envelope 结构统一。
3. 客户端可见错误语义统一。

数据约束：
1. server 使用 Postgres，electron 使用 SQLite。
2. server schema 演进仅允许 migration，禁止生产自动建表。

启动约束：
1. 生产启动必须通过 models 与 templates 关键资产校验。
2. 校验失败直接阻断启动。

## 4. 分项目架构事实

### 4.1 frontend

职责：
1. 提供统一交互层与页面状态管理。
2. 按运行形态选择 Web API 或 Electron IPC API。
3. 执行前端会话门禁与空闲保护策略。

关键实现锚点：
1. `frontend/src/api/index.ts`
2. `frontend/src/api/webApi.ts`
3. `frontend/src/api/electronApi.ts`
4. `frontend/src/runtime/alof.ts`

测试基线：
1. 单元测试覆盖核心 API 适配与状态逻辑。
2. e2e 已覆盖登录、下载与主要异常场景。
3. 机构校验与记录更新链路由 server 与 electron e2e 补位验证。

### 4.2 server

职责：
1. 提供 Web API、鉴权、业务编排与异常治理。
2. 维护 Postgres 持久化与 migration 流程。
3. 托管评估调用链并处理 worker 异常回退。

关键实现锚点：
1. `server/src/app.factory.ts`
2. `server/src/app.module.ts`
3. `server/src/common/http/middlewares/request-id.middleware.ts`
4. `server/src/common/http/filters/all-exceptions.filter.ts`
5. `server/src/modules/record/record-evaluator.ts`
6. `server/src/modules/persistence/persistence.repository.postgres.ts`

测试基线：
1. 单元测试覆盖鉴权、异常过滤、配置校验、业务服务。
2. e2e 覆盖接口主链路与主要失败路径。

### 4.3 electron

职责：
1. 托管 Desktop 主进程生命周期与 IPC 通道。
2. 管理本地 SQLite 数据与本地 worker 进程。
3. 统一 IPC 错误语义与日志记录。

关键实现锚点：
1. `electron/main.ts`
2. `electron/bootstrap/lifecycle.ts`
3. `electron/ipc/index.ts`
4. `electron/services/workerManager.ts`

测试基线：
1. 单元测试覆盖 preload、IPC handler 与主要服务逻辑。
2. e2e 覆盖 Desktop 关键业务链路与会话门禁。

### 4.4 shared

职责：
1. 作为跨端契约与领域类型的唯一事实源。
2. 提供 application/domain/contracts/config 的统一导出。

关键实现锚点：
1. `shared/src/contracts/index.ts`
2. `shared/src/application/index.ts`

测试基线：
1. 单元测试覆盖契约 schema 与关键类型工具。

### 4.5 assets

职责：
1. 提供 models 与 templates 运行资产。
2. 作为 server 与 electron 的共同运行时依赖目录。

控制要点：
1. 生产启动执行关键资产存在性校验。
2. 资产版本与发布流程需与业务版本同步管理。

## 5. 全局主链路

业务请求链路：
1. 请求进入传输层（HTTP 或 IPC）。
2. 按 shared 契约校验请求与响应。
3. 进入应用编排并调用持久化适配器（Postgres 或 SQLite）。
4. 返回统一 envelope，并输出可关联 requestId 的日志与审计事件。

模型评估链路：
1. 业务流程触发记录评估。
2. 评估器调用 Python worker 执行推理。
3. 结果回写记录并附带 modelVersion。
4. 关键事件进入异常处理与审计链路。

## 6. 跨项目差异与收敛策略

差异：
1. 传输层不同：HTTP 与 IPC。
2. 持久化不同：Postgres 与 SQLite。
3. 进程模型不同：server 常驻服务与 electron 主进程托管。
4. 健康探针行为不同：Web 走 `/health`，Desktop 当前为本地占位健康信号。
5. worker 启动策略不同：Web 按需拉起，Desktop 登录后预热常驻。

收敛策略：
1. 业务语义统一收敛到 shared。
2. 错误模型统一收敛到安全消息与 envelope。
3. 测试策略采用 unit + e2e 分层，按运行形态分别验证。
4. 鉴权目标一致，机制按运行形态隔离实现。

## 7. 当前关键风险

1. 云侧或 CI 环境若将数据库端口映射到公网或使用弱认证，存在自动化扫洞与入侵落地风险（历史事件已复盘并固化至 ADR-014）；暴露面与口令须纳入变更评审与例行巡检。
2. 质量门禁尚未全量自动化，跨环境稳定性仍依赖人工巡检。
3. 模型资产治理仍缺完整发布清单与回滚证据链自动化。
4. Python 评估链路在高并发场景下仍存在容量与隔离风险。
5. 边界例外治理尚未形成全自动审批与到期回补闭环。
6. 双持久化形态长期演进下，数据行为一致性需要持续回归验证。
